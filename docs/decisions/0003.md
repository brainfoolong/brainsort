# Results are published as a website that CI builds from its own benchmark runs

## Context

The benchmark produces several thousand numbers per machine: 13 algorithms,
4 key types, 12 input patterns, 4 sizes, a dozen metrics. A README cannot
hold them and stays stale; hand-typed numbers cannot be trusted.

## Decision

- **One page, generated.** `scripts/website.py` renders everything in
  `results/` into a single self-contained HTML file with no external
  resources. The README carries only a small deterministic table that
  `scripts/scorecard.py` derives from `results/counts.csv`; CI fails when the
  README block is out of date.
- **CI measures once and publishes.** Every platform job builds, runs the
  test suite, then runs the benchmark on the same binaries and uploads its
  results as an artifact. A final job downloads every artifact, builds the
  page and publishes it on GitHub Pages. Nothing is measured twice.
- **Deterministic first.** The page leads with the counted numbers (bytes
  moved, comparisons, scratch memory), which are the same on every machine
  and are held by the test suite. Timing is shown per machine, in a
  collapsed section, with the machine's description and a note that shared
  runners are noisy.
- **Stable sorts by default.** brainsort is stable; a comparison with
  unstable sorts is shown only when switched on, and always labelled.
- **A timing file describes the code it measured.** Every timing file carries
  a fingerprint over the measured sources (`include/`, `src/`,
  `third_party/`, `CMakeLists.txt`), computed by the benchmark binary and
  again by the page builder over the current tree. A file whose fingerprint
  differs is left out of the page. A commit hash would not do: it is unknown
  for an uncommitted tree, invisible in a shallow clone, and rewritten by a
  history squash.
- **Workstation results are committed.** The developer machine has hardware
  performance counters and no other tenants, which the shared runners lack,
  so its results are kept in `results/` and appear on the page as long as
  their fingerprint matches. When the measured code changes they drop off
  the page until they are re-measured with `scripts/bench.sh`.

## Consequences

The page is always consistent with the code it describes, at the price of
re-measuring the workstation after every change under the measured paths.
A CI run takes as long as its slowest benchmark job, about an hour.
