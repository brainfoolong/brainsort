# The comparator sort partitions, merges natural runs, and sorts large elements through indices

## Context

The comparator overloads ran a plain merge sort (decision 0006): runs of
16 insertion sorted, then merged bottom-up between the array and a buffer
with a branch-free select. It was 1.6x faster than `std::stable_sort` on
random input and that was its only good number. On input with few
distinct values it did the full n log n of work, 5x slower than pdqsort
and no better than the library merge sort; on two distinct values 6x
slower. Input made of a few sorted runs got no credit for them. And on
64-byte elements every pass moved the elements themselves, so nearly
sorted rows by comparator took twice the time of the same rows by key,
which go through records and a permutation.

The Rust crate had none of these problems because its comparator route
hands the slice to the standard library's driftsort after the prescan,
and driftsort is a partition sort with run detection. The C++ side had
to earn the same numbers with its own code.

## Decision

- **A stable quicksort above the merge sort.** A range longer than 512
  elements is partitioned through the buffer: every element is stored
  twice, into the next left slot of the buffer and the next right slot of
  the array (a slot already read), and the cursor of its side advances,
  so the loop has one compare per element and no branch and no dependency
  from one element to the next; the two sides are then slid into place
  with `memmove` and `memcpy`. The pivot is the median of three, or of
  three medians of three from 1024 elements on. A range keeps the pivot
  it was split off to the right of; when its own pivot is not above that
  one, every element is at least the pivot and the elements equal to it
  are stripped off in one partition, which is what makes few distinct
  values cheap (pdqsort's and driftsort's trick). The smaller side
  recurses and the larger loops; after 2 log2 n + 4 levels a range takes
  the merge sort, so the worst case stays n log n. Ranges of up to 512
  elements are merge sorted. Leaf sizes of 128 to 1024 measured the same
  on random input; 2048 doubled the few-unique time.
- **Natural runs first.** Before partitioning, one pass records the
  boundaries of the maximal non-descending runs, reversing strictly
  descending ones in place (which keeps equal elements in order), and
  gives up as soon as it has seen more than i/32 + 32 runs after i
  elements: on unordered input within the first hundred elements, so the
  pass costs nothing there. Long runs are merged bottom-up with the
  existing level machinery on a boundary array instead of a fixed width.
- **Branch-free sorts of sixteen as the initial runs.** The insertion
  sort of the runs of 16 was 30% of the random-input time (half the
  comparisons mispredicted). A stable sort of four with five comparisons
  and only selects, then exact two-ended merges of 4+4 and 8+8 (each end
  takes exactly as many steps as a run has elements, so no bounds check
  is needed and no run can go dry early) replaced it. A lone merge also
  runs from both ends now, two chains in the pipeline; two paired merges
  each from both ends spilled to the stack and lost, so paired merges
  stay one-ended.
- **Elements over 16 bytes are sorted through indices.** The comparator
  route of such elements sorts an array of 32-bit indices by the order
  of the elements they point to (the displaced-element route when the
  prescan found the input nearly sorted, the comparison sort otherwise)
  and permutes the elements once at the end: by following cycles when at
  most an eighth are out of place, through a gather buffer otherwise. The
  passes move 4 bytes per element instead of 64, and a comparator that
  throws leaves the elements untouched. Ranges of 2^32 elements or more
  keep the direct route.

## Consequences

At 100,000 elements on the Ryzen 7 7800X3D (MinGW GCC 15), against the
old merge sort: random int32 by comparator 2.2 to 1.6 ms, few distinct
values 2.2 to 0.56 ms, two values 1.7 to 0.22 ms, organ pipe 0.70 to
0.20 ms, eight sorted runs 0.83 to 0.50 ms; 64-byte rows nearly sorted
1.5 to 0.66 ms, with few distinct values 3.6 to 1.4 ms, random 4.5 to
3.4 ms. Against pdqsort, which is not stable: ahead on everything but
sawtooth input and two-valued 64-byte rows, where the permutation costs
what pdqsort's in-place partition saves. Against `std::stable_sort`:
ahead on every input except sawtooth on integers, whose merge of two
runs that alternate element by element is where a branching merge
predicts perfectly and a selecting one pays full latency; that cell
stays at 0.6x and is documented rather than special-cased.

The golden counts are untouched: the comparator route is not counted.
The comparator sort uses the buffer of n elements it always did, plus two
index arrays of 4n bytes for elements over 16 bytes and, for the run
detection, an array of n/32 + 34 boundaries. A comparator that throws
still leaves every element in the range: the partition puts the lefts
back into the gap it read them from, the merges copy the side that holds
everything back, and the sort of sixteen writes only after its last
comparison or restores from its buffer.
