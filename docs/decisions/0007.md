# The datasets and the counted path use no implementation-defined standard library behaviour

## Context

The first run of the golden test on macOS (Apple Clang, libc++) reported
380 of 1,689 cells as different, and the same 380 came out of a Clang build
against libc++ on Linux, so it was the standard library, not the compiler
or the CPU:

- `std::uniform_int_distribution` is implementation-defined: libc++ draws a
  different sequence from the same `mt19937_64` than libstdc++, and MSVC has
  its own. Every input built with it differed (`random` int32 keys, the
  swaps of `nearly_sorted`, the run lengths and keys of `runs`, the pool of
  `few_unique`), and with them every count on those inputs. The `sorted`
  and `reverse` int32 inputs differed too without the test noticing: the
  output fingerprint is over the element ids, which a sorted input has in
  order whatever the keys are, so only the radix cells (which read the key
  bits) showed it.
- brainsort took the median of its pivot sample with `std::nth_element` and
  a key-extracting comparator. The median came out the same, but the number
  of comparator calls, and so of key extractions the counted path tallies,
  is a property of the standard library's algorithm.
- gfx::timsort keeps its scratch in `std::vector`, whose growth policy, and
  the `std::copy`/`std::move`/`std::rotate` it runs on, are the standard
  library's.

MSVC did not get that far: `windows.h` defines `min` and `max` as macros
and the benchmark and the API benchmark use `std::min` / `std::max`.

## Decision

- **The generator draws its own integers and reals** (`uniform_u64`,
  `uniform_i64`, `uniform_real` in `include/sortbench/datasets.hpp`): a
  rejection loop on the masked low bits of the 64-bit draw, and the top 53
  bits of a draw for a double. The datasets are a function of the seed alone.
- **The pivot sample median is taken on the extracted keys**, which the
  sample loop already had, and the pivot is the first sample element with
  that key. No standard algorithm with a hooked comparator runs on the
  counted path.
- **gfx::timsort is toolchain-owned**, like `std::sort` and
  `std::stable_sort`: a difference in its cells is printed as a warning,
  not counted as a failure.
- **`NOMINMAX`** is defined before every `windows.h` include.

## Consequences

- `results/counts.csv` was regenerated: every cell on a generated input
  changed (the inputs did), and the brainsort cells with a pivot sample lost
  the key extractions of the median search.
- A Clang build against libc++ passes the golden file with the same three
  toolchain warnings as every other platform. libc++ can be reproduced on a
  Linux machine without root by extracting the `libc++-18-dev`,
  `libc++abi-18-dev` and `libunwind-18-dev` packages and compiling with
  `-nostdinc++ -isystem <dir>/include/c++/v1 -nostdlib++ -lc++ -lc++abi`.
- The tree's code fingerprint changed, so the committed workstation timing
  files are stale until re-measured; the inputs they were measured on no
  longer exist.
