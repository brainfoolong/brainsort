# The opponents are the sorts that can do what brainsort does, upstream and stable

## Context

The benchmark pool had grown three kinds of opponent: the upstream code as
shipped (`std::sort`, `std::stable_sort`, `pdqsort.h` in both partitions,
cpp-TimSort), our own instrumented ports of introsort, TimSort, pdqsort,
merge sort and heapsort, and two textbook radix baselines. The Rust pool
had the two standard sorts and three radix crates (radsort,
voracious_radix_sort, rdst). Every table and tile then carried two
numbers, "against the stable sorts" and "against every sort", and a switch
for the unstable ones.

Two things were wrong with that. The pool compared sorts with different
jobs: an unstable sort may reorder equal keys and a radix crate sorts
scalar keys only, so a loss to them says nothing about brainsort's job,
and a win over them is worth little. And the ports were our own code:
measured 5% to 50% slower than the upstream they follow (decision 0004),
and a port can carry a mistake the original does not.

## Decision

An opponent must be able to do everything brainsort does, and must be the
code that ships:

- **stable**;
- **every key type of the harness** (integers, doubles, strings), so no
  radix sort for scalar keys only;
- **an arbitrary comparator**, so the comparator overloads are compared as
  well;
- **upstream code, unmodified**: vendored or taken from the toolchain,
  never an implementation written here.

The C++ pool is `std::stable_sort` (libstdc++, libc++ and the MSVC STL,
whichever the build uses; libc++ 20+ switches to a radix sort for integers
under the default comparator), cpp-TimSort 2.1.0, and Boost.Sort 1.92.0's
`spinsort` and `flat_stable_sort`. Boost.Sort takes its scratch from
`std::malloc`, which the harness's operator new replacement does not see;
its headers are included with `malloc` and `free` redirected to counted
twins, so the code stays as shipped and its scratch is counted.

The Rust pool is `slice::sort` (driftsort), `slice::sort_by_cached_key`
(the same sort on a buffer of keys and indices, the standard library's
route for a sort by key; not on strings, whose key would be the string
itself) and the glidesort crate. The Rust ecosystem has no fourth common
stable comparator sort; the list is not padded with a rarely used port.

Considered and left out, with the reason:

| sort | reason |
|---|---|
| `std::sort`, `pdqsort.h`, `slice::sort_unstable`, `voracious_sort`, rdst | unstable |
| radsort, `voracious_stable_sort` | scalar keys only, no comparator, no strings (and voracious reordered equal keys on reversed input at a million elements, decision 0010) |
| scandum fluxsort, quadsort, blitsort, wolfsort | stable upstream C, but the qsort interface moves elements as bytes: no `std::string`; wolfsort integers only |
| ska_sort_copy | not stable (falls back to ska_sort) |
| Boost spreadsort, ips4o | unstable |
| cpp-sort | adapts and alters the upstream code it wraps |
| WikiSort, EASTL merge_sort and tim_sort | stable and upstream; not added, the pool of four is enough and each brings its own vendoring cost |
| dmsort | not stable |
| rayon par_sort | stable, but multi-threaded: a different comparison |
| our ports, the radix baselines | not upstream |

## Consequences

- One number per claim: brainsort against the other sorts. The "against
  every sort" columns, the unstable switch and the radix-baseline switch
  are gone from the README, the scorecard and both website pages.
- The harness no longer needs the instrumented ports, so
  `include/sortbench/algorithms/` holds only brainsort's entry; the counts
  of what an in-place quicksort or a timsort does come from the upstream
  code through the traced element wrapper, as before.
- `--all-algos` is gone from `sortbench`: every registered algorithm runs.
- The golden files, the committed workstation timings and the README
  scorecard are regenerated; the website's API tables take their opponent
  columns from the header row of each file, so a change of pool changes
  no parser.
- `results/rust-counts.csv` keeps its `key_reads` column: it is now the one
  pass over the keys `slice::sort_by_cached_key` makes.
