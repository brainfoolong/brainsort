# The Rust sorts are counted as shipped, on what a Rust program can observe

## Context

The C++ harness counts what every sort does: the upstream code as shipped
(libstdc++, pdqsort.h, cpp-TimSort) runs unchanged on a wrapper element
whose copy, move, assignment and comparison operators count, so bytes
moved, reads, writes, comparisons and a cache model exist for every
algorithm. The Rust page of the website had no counterpart: its
deterministic section showed the C++ pool under C++ names, and a Rust
reader had no counted comparison with the sorts a Rust program actually
has, `slice::sort` (driftsort), `slice::sort_unstable` (ipnsort) and the
radix crates radsort, voracious_radix_sort and rdst.

The C++ technique does not carry over. A move in Rust is a bitwise copy
with no hook, and the standard library sorts move elements through raw
pointer reads and writes, so no wrapper type can observe them. What a
Rust program can observe of a sort it did not write:

| metric | as shipped, no port |
|---|---|
| comparisons, and their flips | yes, in the comparator it is given |
| key reads of a radix crate | yes, in the key trait it asks for |
| scratch memory: the peak | yes, through the global allocator |
| element reads, writes, bytes moved | no |
| cache-model misses, the access sequence | no |

The rest would take instrumented ports of driftsort, ipnsort and the crates,
kept in step with the toolchain, which is the same caveat the C++ ports
carry and a few thousand lines of unsafe code each.

## Decision

- **`rust/brainsort-bench` counts every Rust sort as shipped** on the cells
  of `results/counts.csv`: the four harness key types, the twelve inputs,
  1,000 to 1,000,000 elements, the same seed. The comparator and the key
  functions count on the calling thread; a global allocator, armed per
  thread around one call, records the peak of the bytes live. The number
  of allocations is not recorded: for a crate built without hooks it is a
  property of the optimiser, which elides dead allocations in a release
  build, not of the algorithm (voracious made 60 allocations in a debug
  build and 56 in release, with the same peak). rdst runs with its
  single-threaded tuner and no parallelism. A warm-up takes one-time state out of the counted windows:
  brainsort's CPU and cache detection, and the thread pool rdst starts on
  its first call.
- **The file is `results/rust-counts.csv`**, one row per (type, input,
  algorithm, size): comparisons, compare flips, key reads, scratch peak,
  an order hash, and `ok` with the reason when a sort's output failed the
  check. Stable sorts must reproduce the stable reference;
  unstable sorts must sort and permute. `scripts/counts.sh` and
  `counts.ps1` regenerate it after the C++ file when cargo is installed.
- **brainsort's row comes from the counted view** the golden test uses,
  with its scratch taken through the same allocator hook as everyone
  else's. The check holds that row to the trace's own accounting and to
  `counts.csv`, so the two files cannot drift apart. Key reads are left
  empty for brainsort: its key work is counted as table accesses in
  `counts.csv`, a different unit.
- **The test suite recomputes the file**: `cargo test` up to 10,000
  elements in a debug build and 100,000 in release,
  `brainsort-bench --rust-golden` up to 100,000 in CI, next to the C++
  golden check. Any changed count fails.
- **The website's Rust page shows this file** in its deterministic section,
  with the Rust sorts as the opponents and the metrics that exist:
  comparisons, compare flips, scratch memory, key reads. Bytes moved and
  the cache model stay on the C++ page, and the Rust page says why.

## Consequences

- A Rust reader gets a real counted comparison on comparisons and scratch
  memory against every sort a Rust program can call, and no claim on bytes
  moved against them.
- The first run found something: `voracious_stable_sort` is not stable on
  reverse-sorted input with equal keys at a million elements (it detects the
  descending run and reverses it in place). The row is in the file with
  `ok = 0` and the reason, and is excluded from every comparison, as a
  failed row of the C++ file is.
- Instrumented ports of driftsort and ipnsort remain an option if bytes
  moved against the Rust standard library ever matters; nothing here
  prevents adding them as further rows of the same file.
