# Radix digit width: 16 bits on the whole-array path, capped at 13 on the split path

## Context

brainsort's radix route scatters elements into buckets by one digit of the
key per pass. Wider digits mean fewer passes but larger count tables: 11 bits
need 8 KiB of tables per pass, 16 bits need 512 KiB. Textbook advice prefers
narrow digits so the tables stay in the first-level cache.

## Decision

- When the whole array goes through one radix sort, the digit is 16 bits: two
  passes for a 32-bit key. Measured on random int32 keys, two 16-bit passes
  beat three 11-bit passes (0.420 against 0.479 ms at 100,000 elements on a
  Ryzen 7 7800X3D); the 1 MiB L2 holds the tables.
- When the range was first split at a sampled median and each half is radix
  sorted through a half-size buffer, the digit is capped at 13 bits (64 KiB of
  tables). The reason is the allocator, not the cache: a 512 KiB table is
  above glibc's 128 KiB mmap threshold and is mapped and unmapped on every
  call. A single whole-array radix allocates it once and the allocator's
  dynamic threshold hides the cost, but the split path makes two radix calls
  of changing sizes, which defeats that heuristic and made few-unique int32
  input 1.9x slower from page faults alone (337 against 611 us, confirmed by
  forcing a heap-only allocator). Under the threshold the tables stay on the
  heap and are reused.
- The count tables are allocated once per sort and reused across the radix
  calls within it.

## Consequences

The split path sometimes needs one pass more than 16-bit digits would; on the
high-entropy input that splits, the halved working set pays for it. Scratch
memory on random input is about n/2 elements instead of n.
