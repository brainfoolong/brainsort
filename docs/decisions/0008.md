# The Rust port is the same algorithm, proven by the golden counts, and ships with the C++ under one version

## Context

A Rust crate of brainsort was wanted: the same algorithm, the same
contract, published on crates.io, tested and benchmarked like the C++.
Two ways were open: write a radix sort "in the spirit" of the C++ and
call it a port, or port function by function and prove the equivalence.
The C++ benchmark harness counts every element read and write, every
comparison and table access, the scratch memory and the exact sequence of
accesses through a fixed cache model, and holds the C++ to a golden file
of those numbers; the same instrumentation seam exists for a port.

## Decision

- **Function by function, against the golden file.** The port keeps the
  view-and-hooks structure of the C++ (`Arr`, `Hooks`, `Alloc`), the same
  constants, thresholds and hook call sites. The bench crate reproduces
  the C++ harness (the element types, the datasets from a port of
  `std::mt19937_64` and the harness's own uniform draws, the trace with
  the cache model) and recomputes every brainsort row of
  `results/counts.csv`; all 34 columns must match, the trace hash and the
  cache-model misses included. This is what "the same algorithm" means
  here, and it is part of CI (`rust.yml`, job `golden`). It even pins the
  allocation sequence: the C++ heap-allocates the 16-byte handle objects
  of its scratch buffers, so the port allocates the same 16 bytes at the
  same points.
- **The key model.** `key_traits<K>` became the `Key` trait: a
  compile-time `Shape` (up to 32 leaves, fixed bits or bytes, each
  possibly reversed), a leaf writer, and the natural order. The variadic
  composite record became a record whose storage is a nested tuple of
  slots typed by the key (`K::Slots`), so its size is known at compile
  time without const generics; the record type is chosen by a plain `if`
  chain on the shape, which rustc resolves at monomorphisation (dead
  branches are not instantiated; verified on the compiler).
- **Two key functions instead of one.** `sort_by_key` (owned keys, kept
  for the sort) and `sort_by_key_ref` (borrowed keys, read in place),
  because one closure signature cannot return either.
- **A comparator gets the standard library's stable sort**, after the
  same in-place handling of sorted, reversed and nearly sorted input. The
  C++ merge sort was not ported: driftsort is the state of the art the
  ecosystem ships, and a port would have been measured against it and
  lost.
- **Bitwise moves for every element type.** Rust has no self-referential
  values behind `&mut [T]`, so the permutation and the in-place routes
  move any element bitwise; panics are covered by guards that put every
  element back (the slice unchanged when the panic hits the first pass).
  Allocation never aborts: every buffer goes through the crate's `Alloc`
  and a failure falls back to the standard sort.
- **One version, one release.** The crate carries the C++ version number;
  the release workflow (`release.yml`) runs on a `vX.Y.Z` tag, checks
  that the tag, `config.hpp` and `Cargo.toml` agree, tests both, publishes
  the crate (Trusted Publishing, with a token secret as the fallback the
  first release needs) and creates the GitHub release with the single
  header attached.
- **The timing benchmarks measure one set of 100,000 elements** with few
  repetitions, in both languages; more sizes are an option of the
  scripts. Timing is indicative and machine-bound, the deterministic
  counts are the measurement and keep every size.
- **The website shows both languages**, each against its own ecosystem
  as shipped, and pairs the two brainsorts only where a cell was
  measured in both languages on the same machine id, size, type and
  input. The Rust files carry a fingerprint of the Rust sources, so stale
  Rust numbers drop off the page like stale C++ ones.

## Consequences

- The Rust port is not "a Rust radix sort": every planner decision, split,
  dictionary attempt and skipped pass happens where it happens in the C++.
  A change to the algorithm on either side breaks the golden test on the
  other until both are updated, which is intended.
- The published crate has no dependencies; the opponents of the benchmark
  live in the private bench crate.
- The scalar build (`--cfg brainsort_no_simd`) runs under Miri; the
  vector build under AddressSanitizer; a libFuzzer target and a smoke test
  share one body.
