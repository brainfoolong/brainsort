# Ordered input is handled on the elements, and comparators get a merge sort

## Context

The public API built records for every input and recognised only fully
sorted and fully reversed input on the elements themselves, through the
radix form of the keys. Doubles lost half their speed on sorted and
reversed input to the key transform; nearly sorted input paid the records,
the displaced-element route on the records and a full gather permutation;
and a call with a comparator went to `std::stable_sort`.

## Decision

- **One prescan on the elements decides.** Before any record is built, a
  pass over the keys counts descents and ascents and stops as soon as the
  counts prove the input unordered (a few hundred elements into random
  input, so an expensive projection is called few times there). Sorted
  input returns; reversed input is reversed in place, the tie groups put
  back in input order, none when every pair was a descent; nearly sorted
  input (at most n/16 descents) goes to the displaced-element route on the
  elements themselves when they are trivially copyable and at most 16
  bytes, and through the records with a cycle-following permutation, which
  moves only the elements that are out of place, when they are larger. The
  in-place route rewrites every element after the first displacement, so
  on 64-byte rows it lost to the records (1.34 against 0.74 ms); the sparse
  permutation ties pdqsort there. Floating-point keys are compared as
  values, which is their radix order except for NaN; a NaN seen in the
  prescan sends the input to the records, which know its place. Plain
  arrays of 32- and 64-bit numbers are scanned with AVX2.
- **A comparator gets the library's own merge sort.** Stable, bottom-up,
  between the array and a buffer of the same size so that no level copies
  back, with runs of 16 insertion sorted first and a pair of runs that is
  already in order copied instead of merged. The merge selects the side to
  take from instead of branching on the comparison, and two independent
  merges advance together (two pairs of runs while pairs are many, the two
  halves of one pair, found by a merge-path search, once they are few) so
  that the load-after-compare latency of one merge overlaps the other's.
  Trivially copyable elements behind a contiguous iterator only: the buffer
  holds plain copies, so a comparator that throws leaves every element in
  the range, in an unspecified order, which is what `std::stable_sort`
  guarantees. Other element types keep `std::stable_sort`. The prescan
  applies to comparators too.

## Consequences

Sorted and reversed input now runs at memory speed for every key type
(int32 sorted 0.053 to 0.012 ms, double reversed 0.22 to 0.058 ms at
100,000 elements); nearly sorted small elements finish in about half of
pdqsort's time. The comparator path runs 1.6x faster than `std::stable_sort`
on integers and 64-byte rows and stays behind pdqsort, which is not
stable; on inputs with few distinct keys it gains nothing over the
library's merge sort. A projection that throws after the prescan, inside
the in-place route, no longer leaves the range unchanged: during the scan
and the index sort the route restores it, during the final merge the
elements that were not merged yet are put back, so every element stays in
the range.
