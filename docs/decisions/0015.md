# Tests beyond the contract of the sort

## Context

Both libraries were sanitized, fuzzed and, on the Rust side, run under
Miri, and every test fed them what the contract asks for: a comparator
that is a strict weak order, inputs of the size the fuzzer's byte budget
allows, and vector kernels exercised through whole sorts in buffers with
room around them. Four things were not covered.

- A comparator that is not an order. The comparison sort's small merges
  take from both ends without a bounds check, on the argument that the m
  smallest and the m largest of two runs of m are disjoint, which only a
  consistent comparator guarantees. Nothing tested what such a comparator
  got.
- The routes that start at thousands of elements (the key inference, the
  scatter beyond the cache, the index route) were reached by unit tests
  only: the fuzzers cap an input at 8 KiB.
- Miri cannot interpret the AVX2 and BMI2 intrinsics, so the vector
  kernels, the largest share of the unsafe code in the Rust crate, had
  only the whole-sort tests, whose buffers hide an overread of a tail.
- The standard library's own assertions were off in the sanitizer jobs.

## Decision

- **A comparator that is not a strict weak order gets an unspecified
  order and every element exactly once.** The fuzz bodies feed one that
  answers at random, one that answers from a hash of the pair (consistent
  but not transitive), and two total orders no byte window of the element
  expresses, on 16- and 32-byte elements, plain and through the key
  inference. Only the permutation is checked for the first two. The C++
  merge of two exact runs now checks after the fact whether its two ends
  met, and redoes the merge with bounds checks when they did not: one
  pointer compare per sixteen elements, never taken for a comparator that
  keeps the contract. The index permutation's cycle walk ends on any
  index array instead of spinning on one that is not a permutation. In
  Rust the comparison sort is the standard library's, which may panic on
  such a comparator, as its documentation says; the fuzz body swallows
  exactly that panic and still requires a permutation. The ranges C++
  hands to `std::stable_sort` keep the standard library's requirement.
- **A size byte in the fuzz input.** One input in eight is repeated up to
  64 times, so an 8 KiB input reaches 100,000 elements. A nightly workflow
  runs both fuzzers for thirty minutes with the corpus kept between runs;
  the push workflows keep their three minutes.
- **Every vector kernel against its scalar twin**, in both languages, on
  buffers of exactly the size the kernel is told about, over every tail
  length and a few sizes past the commit block. Results are compared byte
  for byte where the contract makes them equal; the scout and the prescan,
  which may stop early on a rule they test at other positions than the
  scalar loop, are compared exactly below the first check and held to the
  rule on a prefix above it. The test found two defects in the split
  kernels of both languages: the scalar tail read its reference key from
  the first element after the vector loop had compacted over it, which
  could set or miss bits of the mask that decides which radix passes run
  (unreachable through the sort, which starts the split at a thousand
  elements, but the mask is trusted as exact); and the tail gave up when
  the buffer was exactly full even when every remaining element was kept,
  a spurious overflow that costs a second pass. The timed scalar splits
  had the second defect too, so the counted and the timed paths could
  disagree on a retry. All three now overflow only on a buffered element.
- **Standard library assertions under the sanitizers.** A CMake option
  turns on `_GLIBCXX_ASSERTIONS` and libc++ debug hardening; the
  sanitizer jobs set it.

## Consequences

- The fuzz bodies changed their input layout (mode byte, size byte,
  elements); the corpora start over.
- The nightly fuzz workflow is the first scheduled job of the repository.
- The kernel tests are unit tests of internals and change with them; they
  are the place to look first when a kernel is edited.
