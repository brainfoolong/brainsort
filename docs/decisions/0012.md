# A plain range of 64-bit keys is sorted without an index

## Context

Every key sort goes through records: the radix form of the key and the
original index, sorted by the core algorithm, then one permutation of the
elements. For a plain array of 64-bit numbers the index is dead weight:
the elements are the keys, the sorted keys are written back directly, and
two elements with equal keys are the same value, so nothing is lost by
not knowing which was which. The 16-byte `Rec64` still cost every pass of
the sort twice the bytes of the key, and the vector kernels handled two
elements per vector instead of four. At 100,000 elements the API
benchmark showed `int64_t` and `double` behind the fastest radix crate
(0.73x to 0.9x in Rust) while the same keys inside a record were ahead.

The one exception is the `double` zero: `-0.0` and `+0.0` compare equal,
share a radix key, and must come out in input order with their bit
patterns intact. The 16-byte record used its spare word to remember a
negative zero.

## Decision

- **A keys-only element type, `Key64`.** Eight bytes, the signed form of
  the radix key, with its own vector layout (`SimdKind::k64`: every lane a
  key, four per vector). The scout, the median split, the partition sort
  and the reversal have kernels for it; everything else in the algorithm
  is generic over the element. The record types are untouched: an
  element that is not its own key, or a key that does not invert from
  its radix form, still goes through `Rec64`.
- **Taken for every self-keyed 64-bit key that inverts.** `int64_t`,
  `uint64_t`, `double`, pointers, enumerations, `chrono` durations and
  time points, and any user `key_traits` with `exact` (in Rust every
  `Key` with `EXACT_FIXED`, and `f64`): the range's own elements are the
  keys, the sorted keys are written back from their radix form. 32-bit
  keys keep the 8-byte `Rec32`, which is already the size of the key
  array; a keys-only 4-byte element would need the vector kernels for
  eight lanes and is left for later.
- **Negative zeros by rank.** The build pass counts them. If there are
  any, a second pass over the still untouched range records, for each
  negative zero, its rank among all zeros in input order. After the sort
  the zeros are one run of equal keys, kept in input order because the
  sort is stable, so the run is found by bisection and the recorded ranks
  put the sign back. Nothing is allocated for input without a negative
  zero, and the pass that reads the doubles a second time runs only then.
- **Both languages, no golden change.** The C++ header and the Rust crate
  take the route under the same conditions with the same passes. The
  deterministic counts are of the algorithm on the benchmark's own
  element types, so they are unchanged; the API tests of both languages
  cover the route with heavy mixes of both zeros, NaNs, full-range
  integers, pointers, and allocation failure at every point, including
  the rank array.

## Consequences

At 100,000 elements on the Ryzen 7 7800X3D, the API benchmark (three
repetitions, so the numbers move by about a tenth between runs). C++,
MinGW GCC 15: `int64_t` random 0.92 to 0.82 ms and with few distinct values
0.26 to 0.21 ms; `double` random 1.02 to 0.89 ms and few distinct values
0.37 to 0.32 ms. Rust, Windows: `i64` random 0.99 to 0.72-0.79 ms over two
runs, few distinct values 0.22 to 0.17 ms; `f64` random 0.98 to 0.77-0.84
ms, few distinct values 0.30 to 0.23 ms; against the fastest radix crate
the random rows went from 0.90x to level or ahead. WSL2, GCC 13: C++
`int64_t` random 0.97 to 0.79 ms, `double` random 1.08 to 1.05 ms; Rust
`i64` random 0.92 to 0.80 ms and `f64` random 0.95 to 0.77 ms, from 0.74x
and 0.89x of the fastest radix crate to 0.94x and 1.08x.

The memory of such a sort halves: 8 bytes per element for the keys plus
about 4 per element of scratch on full-entropy input, where the records
took 16 and 8. Sorting a `double` range with negative zeros costs one more
pass over the range and an array of 4 bytes per negative zero.

Nothing changes for keys of up to 32 bits: `Rec32` is 8 bytes, and a
4-byte keys-only element would need eight-lane vector kernels. That is
the remaining step of this kind, and it is left until the numbers ask for
it: `int32_t` random already sorts at 0.45 ms against 1.56 ms for
pdqsort.
