# Plain 32-bit keys are sorted without an index

## Context

Decision 0012 sorted a plain range of 64-bit keys as the keys themselves,
8 bytes per element instead of a 16-byte record, and left the 32-bit keys
on their 8-byte records because the vector kernels would have to handle
eight lanes. The API benchmark then showed where the time of an `int32_t`
sort goes at 100,000 random keys: 0.37 ms of 0.43 in the record sort, the
rest in building the records and writing the keys back. `int32_t` is the
most common key there is, and half of every byte the record sort moved was
an index nobody needed.

The comparator sort with an inferred key (decision 0013) had a second
cost: its verification pass asked the comparator twice about every pair
of neighbours and walked the indices of every run of equal elements, and
its search for the window tested every narrower window after a wider one
had already agreed. On `int32_t` with few distinct values, where almost
every pair is equal, that pass cost as much as the sort.

## Decision

- **A 4-byte keys-only element, `Key32`.** The signed form of a 32-bit
  radix key, with its own vector layout (`SimdKind::k32`: eight keys per
  vector). The scout, the median split, the partition sort and the
  reversal have kernels for it; the compress permutation for eight lanes
  is a 2 KB table of byte indices widened on use. The partition sort for
  two to four distinct keys, which decision 0012 kept to 8-byte elements,
  takes 4-byte elements as well.
- **Taken for every self-keyed key of up to 32 bits.** `int32_t`,
  `uint32_t`, the 8- and 16-bit integers, `char`, `bool`, `float`,
  enumerations and any exact `key_traits` of up to 32 bits (in Rust every
  `Key` with `EXACT_FIXED` of up to 32 bits, and `f32`): the range's own
  elements are the keys, and the sorted keys are written back. The keys
  live in their own buffer, as with `Key64`: the core allocates scratch
  while it runs, so sorting the caller's array in place would leave it
  half permuted when an allocation fails. `float` gets the negative-zero
  rank pass of `double`. `Rec32` remains for keys that are not the
  element, or elements whose key does not invert.
- **The inferred sort verifies with one comparator call per pair.** Two
  neighbours with the same window key were left in index order by the
  stable sort, so they only have to not descend, one call. Where the key
  changes, the three-way outcome decides whether a class of the
  comparator ends, the guess failed, or one class spans two keys; only
  such a spanning class is sorted by index, with its start found by
  walking back over the same-key pairs. The search for the window stops
  at the first width where a window agrees, since a narrower one cannot
  win. The result is what it was on every input; the API tests of both
  languages cover the coarse, the finer and the adversarial comparator.
- **Both languages, no golden change.** The deterministic counts are of
  the algorithm on the benchmark's own element types, which do not take
  the route; the golden checks of both languages pass unchanged. The
  crate also compiles on Rust 1.86 again, its stated minimum: the
  inference entry point used a `let` chain.

## Consequences

At 100,000 elements on the Ryzen 7 7800X3D, pinned, three repetitions.
C++, MinGW GCC 15: `int32_t` random 0.55 to 0.38 ms, from 2.9x ahead of
pdqsort to 4.0x; with few distinct values 0.23 to 0.19 ms, from 1.8x to
2.1x. Rust, Windows: `i32` random 0.40 to 0.37 ms, from 0.96x of the
fastest radix crate to 1.07x; few distinct values 0.17 to 0.14 ms, from
1.35x to 1.6x. WSL2, GCC 13: C++ `int32_t` random 0.46 to 0.37 ms and few
distinct values 0.26 to 0.24 ms; Rust `i32` random 0.40 to 0.37 ms, from
0.78x of the fastest radix crate to 0.83x, few distinct values 0.17 to
0.14 ms, from 0.89x to 1.09x. In an unpinned harness at 1,000,000 keys the
C++ `int32_t` sort went from 4.4 to 3.3 ms on random keys and from 1.9 to
1.5 ms on few distinct values.

The inferred comparator rows moved less than the run-to-run noise:
`int32_t` by comparator with few distinct values 0.375 to 0.364 ms in C++
(1.1x of pdqsort) and 0.354 to 0.337 ms in Rust. The verification now
costs one comparator call and one key compare per pair on every input,
which is what it costs on random keys; the row is bounded by the record
sort with its index and the gather, which stay.

The memory of a plain 32-bit sort halves: 4 bytes per element for the
keys plus about 2 per element of scratch on full-entropy input, where the
records took 8 and 4. A `float` range with negative zeros costs one more
pass over the range and an array of 4 bytes per negative zero.

What remains for `int32_t` by comparator is the record sort with its
index, needed to gather the elements and to keep classes of a coarser
comparator in input order; a keys-only inferred sort would have to redo
the sort through records whenever the verification finds such a class.
