# Large inputs scatter once by their top digit, and freed memory is kept

## Context

The public-API benchmark against `std::sort`, `std::stable_sort` and
pdqsort showed two kinds of loss that the algorithm's design did not
explain. At ten million elements the 16-byte records lost to pdqsort
(0.7x): every radix pass streamed 80 MB per half through 8,192 write
streams, which the cache cannot hold. At a hundred thousand elements
several cells lost although the algorithm itself finished in a fraction of
the time: each call allocated a few blocks of fresh memory, and the page
faults of first touch cost as much as the sort.

## Decision

- **An MSD scatter beyond the cache.** A part larger than a third of the
  last-level cache is scattered once by its top key bits into buckets of
  about the size of the first-level data cache, and each bucket then takes
  the fused LSD passes in cache. The scatter goes through write-combining
  buffers, one cache line per bucket, written to the array whole and
  aligned with non-temporal stores; the thousands of write streams cost one
  line write each instead of a read-for-ownership and a partial write per
  element. The pass count is unchanged; what changes is that all but the
  first pass run in cache. Below the threshold the passes fit the cache
  already and the extra histogram per bucket cost more than the scatter
  saved (at 4 MB per half, 1M int32 went from 5.0 to 7.0 ms), so the
  threshold matters: a third of the last-level cache is where the two
  buffers of a pass stop fitting, measured at 16 and 32 MB per half on a
  96 MB cache. The cache sizes are read from the CPU (`cpuid` leaf 4, or
  `0x8000001D` on AMD), with desktop defaults where nothing can be read.
  Bucket sizes of half and twice the first-level cache, 128-byte lines, and
  16-bit counters for the bucket passes were measured and lost; a single
  wide pass through the buffers lost too, because the copy back that a
  one-pass sort needs then reads the result from memory.
- **Freed blocks are kept.** The library keeps up to 32 MiB of the blocks
  its sorts free (`BRAINSORT_MEMORY_CACHE`), process-wide under a mutex
  taken a few times per sort, and the next sort takes them back warm; a
  block carries its capacity in a 16-byte header. A per-thread cache was
  the first version and crashed on MinGW: its emulated thread-local storage
  runs the destructor of a thread-local object after the thread's heap
  state is gone. The shared cache has no destructor at all; the process
  returns the memory, or `brainsort::release_memory()` does.
- **The result may stay in the scratch buffer.** The top-level radix of the
  public API no longer copies its result back to the record array; the
  permutation reads it from whichever buffer holds it. A one-pass sort
  (few distinct keys, narrow keys) saves a full pass.
- **Doubles are written back from their records.** The radix transform of a
  double is a bijection on every bit pattern except that `-0.0` and `+0.0`
  share a key, so a sort of a plain `std::vector<double>` remembers a
  negative zero in the record's spare word and writes the sorted values
  back directly, like integers, instead of permuting the array through a
  gather buffer.

## Consequences

At ten million elements every random cell now beats pdqsort (int64 278 to
174 ms against 194; double 296 to 209 against 228). At a hundred thousand,
the cells that were dominated by page faults halved (int32 few unique 0.65
to 0.21 ms). The library holds up to 32 MiB of memory after a sort until
the process ends or `release_memory()` is called; a program that cannot
afford that sets `BRAINSORT_MEMORY_CACHE` to 0.
