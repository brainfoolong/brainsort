# The comparator sort infers the key it is given

## Context

The comparator overloads were the only rows of the API benchmark where
the library lost: `int32_t` by comparator at 0.7x of the standard
library's unstable sort in Rust and level with pdqsort in C++, while the
same numbers by key sorted three times faster. A comparison sort cannot
beat another comparison sort by much, and driftsort and ipnsort are
good ones. The only way to a radix sort is to know the key, and a
comparator does not say what it compares.

But the elements say something. A comparator that a user writes as
`a.score < b.score` is the order of eight bytes at a fixed offset of the
element, read as a double. A guess of that form can be tested cheaply
against the comparator itself, and a wrong guess can be caught after the
sort, because a sorted result is checked in one pass.

## Decision

- **Guess, sort, verify.** The comparator is asked about a strided
  sample of 2048 adjacent pairs. Every aligned window of the element (an
  integer of 8, 16, 32 or 64 bits, signed or unsigned, a float or a
  double, ascending or descending) is tested against the sampled
  answers; a window that agrees with all of them is sorted as a key
  through the record path with indices, the elements are gathered into a
  buffer in that order, and one sequential comparator pass checks it. A
  pair the comparator calls descending fails the check, the buffer is
  dropped and the untouched range goes to the comparison sort. Among
  windows that agree the widest wins, then a float that no sampled value
  reads as a denormal (integers read as floats are denormals, floats in
  use never are), then signed, then unsigned.
- **Stability by the comparator's classes.** The window may be finer
  than the comparator (a comparator on `key / 1000` is agreed with by the
  window on `key`); then elements the comparator calls equal are sorted
  by the window and not in input order. The verification pass sees them
  as runs of equal elements, and each run is put back into index order.
  The result is what a stable sort by the comparator gives, on every
  input.
- **What it costs when it is wrong.** A comparator that is no window at
  all fails the sample on the first pairs of every candidate: a few
  thousand comparator calls, then the comparison sort as before. A
  comparator that agrees with a window on the sample but not everywhere
  pays the record sort, the gather and the check before the comparison
  sort: about a third more than the comparison sort alone, bounded.
- **From 4,096 elements on.** Below that the sample (every pair, on a
  short range), the records and the check cost more than the comparison
  sort of a short range saves: at 1,000 elements an inferred sort of
  `int32_t` took 8 us against 5 us for `std::sort`, at 5,000 the two were
  level, at 20,000 the inferred sort took a fifth of the time. Short
  ranges take the comparison sort as before.
- **Nearly sorted input keeps its route.** The displaced-element route,
  in place or on indices, runs before the inference: a nearly sorted range
  of 64-byte rows sorted through the inferred key took 1.0 ms where the
  displaced elements alone take 0.6.
- **Automatic in C++, an entry point in Rust.** Reading the bytes of a
  trivially copyable object is defined in C++, so `sort_with` and the
  comparator overload of `sort` infer on every trivially copyable
  element. In Rust a slice of an arbitrary type may hold padding, which
  the language forbids reading, so `sort_by` cannot infer; the crate
  offers `sort_by_inferred` on elements that implement `PlainBytes`, an
  unsafe marker trait that every primitive number and array of them
  implements and a padding-free struct opts into. Its result is that of
  `sort_by`.
- **Not counted.** The comparator route is not part of the golden counts.
  The API tests of both languages cover a key window, a descending one, a
  coarser comparator, an adversarial one that agrees on the sample and
  disagrees on one rare value, a padded struct, and comparators that are
  no window.

## Consequences

At 100,000 elements on the Ryzen 7 7800X3D (three repetitions). C++,
MinGW GCC 15, `brainsort::sort` with a comparator: `int32_t` random 1.55
to 0.55 ms, from level with pdqsort to 2.8x ahead; with few distinct
values 0.64 to 0.38 ms, from 0.64x of pdqsort to 1.1x; 64-byte rows by
their `int64_t` field random 3.3 to 1.5 ms and few distinct values 1.4 to
0.8 ms; sorted, reversed and nearly sorted rows unchanged. Rust,
`sort_by_inferred` against `sort_by`: `i32` random 1.23 to 0.61 ms, from
0.72x of `slice::sort_unstable_by` to 1.5x ahead; 64-byte rows random 2.4
to 1.5 ms. WSL2, GCC 13: C++ `int32_t` random 2.15 to 0.63 ms, from 0.71x
of pdqsort to 2.5x ahead, few distinct values 0.57 to 0.47 ms; 64-byte
rows random 3.6 to 1.5 ms; Rust `i32` random 1.22 to 0.59 ms and 64-byte
rows 2.4 to 1.4 ms.

The comparator rows were the last rows of the API benchmark where the
library lost on unordered input; what remains behind is `int32_t` with
few distinct values against pdqsort's unstable partition, at 0.9x to 1.1x
depending on the run, and every comparator sort below 4,096 elements,
where the comparison sort is what it was.

The Rust `sort_by` is unchanged: it cannot read the bytes of an
arbitrary element type. The benchmark reports both entry points, so the
page shows what a caller gets without the opt-in and with it.
