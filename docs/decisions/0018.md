# The Rust comparator sort merges natural runs and keeps driftsort for the rest

## Context

The C++ comparator sort (decision 0011) is a stable quicksort with a
natural-run merge in front of it and a branch-free merge sort in its
leaves. The Rust crate hands a comparator to the standard library's
stable sort, driftsort, after the in-place routes (decision 0008), and
the question was whether a port of the C++ sort would be faster.

The whole sort was ported: the elements moved bitwise through
`MaybeUninit` slots so that any element type can take the route, drop
guards where the C++ has catch blocks, the same constants. The port was
measured against `slice::sort_by` on the patterns of the C++ harness, on
`i32` elements and on `u32` indices over 64-byte rows (the index route
of elements over 16 bytes), on the Ryzen 7 7800X3D under rustc 1.98,
milliseconds per sort of 100,000 elements:

| input | i32 port | i32 driftsort | indices port | indices driftsort |
|---|---|---|---|---|
| random | 1.26 | 1.21 | 3.76 | 2.21 |
| 100 distinct values | 0.44 | 0.37 | 1.34 | 0.87 |
| 2 distinct values | 0.153 | 0.144 | 0.46 | 0.27 |
| runs of 16 to 2000 | 0.49 | 0.92 | 1.10 | 1.52 |
| 8 sorted runs | 0.29 | 0.56 | 0.57 | 0.91 |
| organ pipe | 0.146 | 0.236 | 0.24 | 0.34 |
| sawtooth of 1000 | 0.64 | 1.21 | 1.59 | 2.07 |

The merge loops compile to compares and conditional moves, as in the
C++, so the numbers are the algorithms'. The quicksort loses on every
unordered input at every size (at 10,000 elements, 100 distinct values:
0.45x on `i32`, 0.37x on indices): driftsort is a partition sort with the
same equal-element stripping and a better small sort, and it sorts the
index route's 4-byte keys with fewer memory operations than a partition
that stores every element twice. The natural-run merge wins 1.5x to 2x
on every input made of long runs, from 10,000 elements up to a million,
on both routes: driftsort finds the runs too, but its merge of them costs
more than the counted, branch-free bottom-up merge of the C++.

## Decision

- **The natural-run merge is ported and runs first.** From 512 elements
  on, `sort_by` finds the maximal non-descending runs in one pass that
  reverses strictly descending runs in place and gives up once it has
  seen more than i/32 + 32 runs after i elements (within a few hundred
  elements on unordered input). Long runs are merged bottom-up between
  the slice and a buffer of n slots with the C++ merges: two merges
  advanced in lock step, one merge from both ends, long pairs split at
  the middle output position. Elements over 16 bytes get the pass on
  their indices.
- **The quicksort is not kept.** When the runs are too short the slice,
  a permutation of the input with the same stable order, goes to
  `slice::sort_by` as before. A slower sort is not worth a thousand lines
  of unsafe code; the numbers above are the record of the attempt, so it
  is not repeated.
- **The guarantees do not change.** The pass moves elements bitwise and
  never drops one; a comparator that panics during a merge leaves every
  element in the slice, because the source of the level in flight holds
  all of them and is copied back. A comparator that is not an order gets
  a permutation: every merge is counted, so no answer moves a cursor past
  its run. If the buffer or the boundaries cannot be allocated the pass
  is skipped.

## Consequences

Input made of sorted pieces, organ pipes and sawtooth waves by comparator
sorts 1.5x to 2x faster in Rust from ten thousand elements on; random,
few-valued, sorted, reversed and nearly sorted input is unchanged, since
the pass gives up or the earlier routes take those. The comparator sort
allocates a buffer of n elements plus n/32 + 34 boundaries when it finds
runs, and n/32 + 34 boundaries when it does not. The golden counts are
untouched: the comparator route is not counted. The C++ and the Rust
comparator sorts now share the run pass and the merges and differ in what
sorts unordered input, which each side's decision record explains.
